# 故障排查

中文 | [**English**](TROUBLESHOOTING.md)

本项目上出现过的症状、其原因，以及——更有用的——每个症状能证明什么、不能证明什么。

反复出现的主题：**好几个看似固件故障的问题，其实是测量故障。** 在断定代码没运行
之前，先核实你读的东西就是代码写的东西。

---

## 构建与依赖问题

### `fetch-deps.sh` 失败："does not apply to ... the upstream revision moved"

`patches/` 中的补丁针对某个特定的上游提交。若某个子模块没落在固定版本上，补丁
上下文就对不上。

```bash
git -C .work/uefi/Mu_Basecore rev-parse HEAD
# 预期：3c9c7b2e211e62d2a954ad760a36fe05adc43aa3
```

修好固定版本；不要手工编辑第三方源码去凑补丁。被悄悄改过的上游，已不再是当初
验证过的东西。

注意：上游 EDK2/Mu 文件使用 CRLF 行尾，所以补丁以 `git apply --ignore-whitespace`
应用。这是预期行为，不是对损坏补丁的变通。

### `build` 报告找不到 `evergoPkg/evergo.dsc`

`--tree` 指向了错误目录，或 `fetch-deps.sh` 从未运行。代码树必须包含
`Platforms/Xiaomi/evergoPkg/evergo.dsc`。脚本会检查这一点，否则拒绝运行。

### 构建在 `Mu_Basecore/BaseTools` 内失败

EDK2 基础工具在首次使用时编译，需要 `make` 和主机 C 编译器。在 macOS 上还要确认
已安装 Command Line Tools。

### `FD size` 不符（不是 2097152 字节）

构建时没带热跳几何参数。请用 `scripts/build.sh`；它总是传入：

```text
-D FD_BASE=0xB0000000 -D FD_SIZE=0x200000 -D FD_BLOCKS=0x200
```

冷启动 FD（基址 `0x40080000`）在 MMU 一开启时就崩溃，看起来像「固件坏了」，
而不是「镜像链接错了」。

### 同一份源码的两次构建产生不同哈希

预期之中。编译器会嵌入构建路径与 PDB 签名。稳定的是模块清单与代码；要比对模块
字节，而不是 FD 哈希。比对方法见 `docs/BASELINE.md`。

## 启动问题

### 什么都没有：手机直接复位回 Android

跳转没生效，或镜像在执行前被拒绝。

按顺序检查：

1. stage1 模块报告了成功（它自己的输出），
2. 镜像就是你构建的那个（两端 `sha256sum`），
3. FD 正好 2 MiB，
4. `BootShim.bin` 是针对当前 FD 重新构建的（shim 在汇编时记录 FD 的大小与基址——
   过期的 shim 会拷贝错误的量）。

**不能证明**固件坏了。

### 出现彩条，然后黑屏

SEC 运行并到达帧缓冲，之后某个东西死了。

这是最有信息量的失败。读信标页：最后的阶段会告诉你 DXE 派发是否完成、BDS 是否
到达 `AfterConsole`、是否到达 UniXNU 启动点。见 README 中的阶段表。

常见原因：

* 从 FV 派发的某个驱动崩溃了（往 `DXE.inc` 里新加了 INF），
* 内存映射不再覆盖下一阶段要触碰的某个地址（在 `MemoryMapLib` 中新增或移动了
  区域），
* FD 被重新构建成与 shim 拷贝目标不同的基址。

### 出现彩条，然后 UniXNU 菜单出现、倒计时在走

这就是已验证状态。它不是失败，也不是 XNU 在启动。

如果菜单不再出现在它以前出现的位置，最可能的原因是启动管理器路径：
`BootManagerLib/BootManager.c` 查找一个特定的 FV 文件 GUID 并启动它。确认该文件
仍在 `DXE.inc` 中、且 GUID 未变。

### 菜单出现，按键无效，屏幕显示 `No input device`

这是已验证构建的已知状态，不是回归。

菜单统计带设备路径的输入设备。在本设备上，菜单查找的时刻没有 `SimpleTextIn` 句柄
到达 `gST->ConIn`。固件里确实有 `KeypadDxe` 与 `KeypadDeviceDxe`；它们相对菜单的
绑定顺序才是未解的问题。

**不要**通过在菜单内直接轮询按键寄存器、或覆写随附的 UniXNU 菜单源码来「修」这个。
两者都在已验证构建之后试过，都没有产生按键事件；后者还破坏了「菜单是上游代码」
这条规则。

### 菜单出现，然后设备复位

倒计时到期了。默认条目是 `Return to firmware`，它让菜单退出，退出后回到 XNU
payload 钩子，钩子找不到 payload 就返回 BDS，BDS 无法启动任何东西，便空转直到
看门狗复位 SoC。

对于一个既无启动项、又无可用输入的固件，这是预期行为。

### 菜单显示 `no boot entry found`

没有向菜单发布任何 payload 卷。这是缺失的功能，不是故障。

## 信标与诊断问题

### 信标页读出全 `0x00` 或全 `0xFF`

该页被覆盖了。它位于 Android 内核管理的预留 ramoops 窗口内，内核会重写其中一部分。

**这对固件是否运行过什么都证明不了。** 把本次运行当作作废，要么重跑，要么读取
loader 写入 payload 窗口的镜像副本。

### 信标页有看似合理的 magic，但槽位是乱码

同样的原因。被部分覆盖的页仍可能显示更早一次运行的 magic。把阶段与屏幕显示的内容
对照；若二者不一致，相信屏幕并重跑。

### 某个阶段标记缺失，但后续阶段存在

某些路径中标记写入一个小环。缺失的中间标记通常意味着它被覆盖了，而不是被跳过。
在断定代码被跳过之前，用一个单调计数器或每次运行唯一的 id 来确认。

### 跟踪环显示的是上一次运行的记录

TRC 环并非在所有路径进入时都清空。给每次运行一个唯一的标记值，并在读取其余内容
之前先检查它。

## 部署问题

### `deploy.sh` 拒绝："ro.product.device is '...', expected 'evergo'"

按设计如此。内存映射是设备专属的；把它刷到别的机型上，正是设备变砖的方式。

### `deploy.sh` 不带 `--yes` 就拒绝

同样是设计如此。每次部署都会复位手机。

### `adb` 在流程中途消失

预期之中：热跳把控制权从 Android 手中交出去。在 Android 回来之前，屏幕是唯一输出。

### 运行后手机没回到 Android

长按电源约 15 秒。热跳路径只改动 DRAM，所以冷复位会恢复 Android。如果它仍不启动、
且你从未刷过任何分区，那问题不在这份固件。

## 在这个项目上节省过时间的规则

1. **先修正测量，再相信测量。** 写地址、读地址、缓存维护地址与读取者的偏移必须
   一致。它们不止一次不一致，而每次不一致都产生了一个自信的错误结论。
2. **每次运行只改一处。** 一串投机性改动会让每个结果都无法归因。
3. **区分「未执行」与「执行了但读到零」。** 只有被测代码写下的标记能区分二者。
4. **干净构建不是启动。** 编译成功对是否到达 BDS 一无所知。
5. **渲染出的画面不是内核进展。** UEFI 画图与 XNU 打印到控制台是不同层次；说清你
   观测到的是哪一层。
6. **不要相信过期的产物。** 构建脚本可能失败，却仍在磁盘上留下一个哈希看似有效的
   旧 FD。检查构建的退出状态与产物的时间戳。
